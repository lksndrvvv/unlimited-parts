# unlimited-parts

Практическая 2 — Программная инженерия

В рамках практических работ 2.0–2.2 был создан учебный проект `Unlimited Parts`.

Изначально задания были рассчитаны на Azure DevOps, но в данной работе основные возможности были перенесены на GitHub: GitHub Issues, GitHub Projects, Board, Backlog и Insights.

Для работы с файлами проекта использовался Visual Studio Code и Git.

## Практическая 2.0 — Подготовка тестовых данных

На этом этапе была подготовлена основа проекта для выполнения следующих практических работ.

Был создан репозиторий `unlimited-parts` и GitHub Project `Unlimited Parts`.

В проекте были добавлены основные поля для управления задачами:

- `Work Type` — тип рабочего элемента;
- `Team` — команда проекта;
- `Sprint` — итерация;
- `Activity` — вид работы;
- `Remaining hours` — оставшееся время;
- `Priority` — приоритет;
- `PUL Ticket ID` — пользовательский идентификатор;
- `Definition of Done` — критерий завершения работы.

Была создана команда:

`PUL-Web`

Настроены три спринта:

- Sprint 1 — завершённый;
- Sprint 2 — текущий;
- Sprint 3 — будущий.

Для имитации структуры рабочих элементов Azure DevOps были созданы типы:

- Epic;
- Feature;
- PBI;
- Task;
- Bug.

Также была подготовлена иерархия рабочих элементов:

`Обучение продуктам`
→ `Осваиваем дашборды`
→ пользовательские истории
→ задачи.

Были созданы labels `data`, `ux`, `development`, `design`, `expedited` и использован стандартный label `bug`.

Таким образом, практическая 2.0 подготовила тестовое окружение, которое далее использовалось в практических 2.1 и 2.2.

## Практическая 2.1 — Scrum-планирование

В этой работе было выполнено планирование проекта по Scrum.

Для команды `PUL-Web` использовались три итерации, при этом `Sprint 2` являлся текущим.

Были настроены рабочие элементы разных уровней:

- Epic — `Обучение продуктам`;
- Feature — `Осваиваем дашборды`;
- три PBI;
- две Task.

Для пользовательских историй использовались разные состояния:

- `New`;
- `Approved`;
- `Committed`;
- `Done`.

Карточки перемещались между состояниями на Kanban-доске, что позволило показать изменение состояния работы.

Для задач были заданы оценки трудоёмкости:

- `Добавить страницу для самых последних учебников` — сначала 5 часов, затем оценка была увеличена до 8 часов;
- `Оптимизация запроса к данным для последних учебников` — 3 часа.

Таким образом, первоначальная трудоёмкость составляла 8 часов, а после переоценки — 11 часов.

Также была смоделирована ограниченная емкость команды и отсутствие сотрудника в течение пяти рабочих дней.

Для просмотра данных были созданы отдельные представления:

- `Backlog`;
- `Sprint 2`;
- `By people`.

Для задач разработки использовался зелёный label `development`, а ошибки представлены отдельным типом `Bug` и label `bug`.

## Практическая 2.2 — Kanban и мониторинг

На этом этапе была расширена Kanban-доска проекта.

К существующим состояниям были добавлены:

- `QA Doing`;
- `QA Done`.

Они используются для отображения этапа тестирования и контроля качества.

Для этапа `QA Doing` был задан лимит незавершённой работы WIP = 1.

Также был добавлен критерий завершения работы:

`Definition of Done: Проходят все тесты`

Для одной из пользовательских историй был установлен повышенный приоритет:

`Priority = Expedited`

и добавлен label `expedited`.

Это используется как аналог ускоренной дорожки в Kanban.

Для мониторинга проекта были созданы представления и диаграммы GitHub Insights:

- `Обучение продукту`;
- `Sprint Overview`;
- `Sprint Effort`;
- `Sprint Capacity`;
- `Веб-задачи`;
- `Веб-задачи — по назначению`;
- `PUL Tickets`.

`Sprint Overview` показывает распределение элементов текущего спринта по статусам.

`Sprint Effort` используется для визуального анализа работ текущего спринта.

`Sprint Capacity` показывает распределение задач по исполнителям.

Представление `Веб-задачи` содержит только задачи команды `PUL-Web`.

Диаграмма `Веб-задачи — по назначению` показывает распределение этих задач по исполнителям.

Также было использовано пользовательское поле:

`PUL Ticket ID`

Для PBI были назначены значения:

- `PUL-001`;
- `PUL-002`;
- `PUL-003`.

Таким образом была показана возможность расширять структуру рабочих элементов собственными полями.

- Epic, Feature, PBI и Task;
